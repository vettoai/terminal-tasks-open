# Console performance work

Ewa Kaczmarek · Frontend performance engineer

With the API and a production console running, use `npm run bench -- --url http://127.0.0.1:3000`. The npm entrypoint runs the driver with the Python browser tools installed in `/opt/console-tools` and system Chromium. Chromium runs headlessly with a 1440×1100 viewport, device scale 1, software rendering and background throttling disabled. Browser launch, service startup and compilation sit outside the measurements. Each run uses a fresh context and warms both interaction kinds before measuring. Toolbar controls are found during warmup and reused for browser input, with another lookup if a control is replaced or moves to another pane. Handles are released when the run ends. Garbage from warmup and graph interactions is collected before each measured phase; allocations and collection during that phase stay on the clock.

The camp_large workload uses ten prerequisite branches and thirty increasing event times spread over the activity period. The adjacent workload.json records those choices from the fixture history; use the same file for both checkouts. Graph milliseconds are mean elapsed time over twenty branch expand/collapse actions, through the accessible edge-list update, layout and canvas paint. Playback milliseconds are mean elapsed time over thirty forward historical steps, through visible state update and paint. The adjacent driver owns the workload, including its browser settings.

Use five runs on each checkout, interleaving the checkouts on the same machine without overlapping workloads. Compare medians. The regression allowance is 20% for each metric: this keeps navigation within our interaction budget while leaving room for correctness work. Sample standard deviation divided by arithmetic mean gives the coefficient of variation. If either metric has CV above 0.10, repeat that five-run set, at most twice. Use the first stable set. Three unstable sets are inconclusive; investigate the machine before signing off performance.

For memory work, use fresh contexts for three runs. Alternate early and late historical times for 200 settled navigations, varying the endpoints and toggling a prerequisite branch each time. Force Chromium garbage collection through the debugging protocol after navigation 100, 150 and 200, then read retained JavaScript heap. MB means 1,000,000 bytes. Growth from 100 to 200 above 10 MB, with 200 also above 150, is sustained growth. Two such runs out of three exceed the retention budget; a stable higher plateau or temporary allocation peak does not. Keep the navigation sequence and browser configuration identical when comparing checkouts.
